# Промпт для реализации Phase 8 — Business Agent

Ты работаешь в репозитории `ai_agent_first` как старший Python-разработчик. Полностью реализуй Phase 8 — Business Agent. Не ограничивайся советами или примером кода: изучи проект, запиши план, создай рабочую реализацию, подключи её там, где это предусмотрено архитектурой, добавь проверки и обнови документацию.

## Цель этапа

Сделай минимальный, но законченный вертикальный сценарий работы с доходами и расходами. Пользователь пишет обычным языком, например:

- «Запиши доход 120000 BYN от клиента Альфа за дизайн сегодня»;
- «Вчера потратил 450 BYN на рекламу»;
- «Добавь расход на аренду 1500».

Агент должен извлечь данные, проверить их кодом, задать точный вопрос по недостающим обязательным полям, показать готовый черновик и сохранить его только после явного подтверждения пользователя. После сохранения запись должна переживать перезапуск процесса и быть доступна только в своей сессии.

Не переписывай работающий runtime и не дублируй `ToolRegistry`, MCP-клиент, Telegram API или общую память.

## Требуемое поведение

Одна бизнес-операция содержит:

- `id` — локальный неизменяемый идентификатор, создаваемый кодом;
- `session` — владелец записи; модель не задаёт это поле;
- `kind` — только `income` или `expense`;
- `amount` — положительная денежная сумма;
- `currency` — трёхбуквенный код в верхнем регистре, например `BYN`, `USD`, `EUR`;
- `occurred_on` — календарная дата ISO `YYYY-MM-DD`;
- `category` — необязательная короткая категория;
- `counterparty` — необязательный контрагент;
- `note` — необязательное пояснение;
- `created_at` — время создания, задаваемое кодом.

Обязательные пользовательские поля: `kind`, `amount`, `currency`, `occurred_on`. Пустые значения и догадки запрещены. Относительные даты «сегодня» и «вчера» разрешено преобразовывать только от явно переданной приложением текущей даты; тесты не должны зависеть от реальных часов. Не угадывай валюту из города, языка или прошлых расчётов. Не преобразовывай валюты автоматически.

Деньги проверяй через `Decimal`: запрети `NaN`, `Infinity`, экспоненциальную запись, ноль, отрицательные значения, лишнюю точность и чрезмерную длину. В SQLite сохраняй нормализованное точное значение без `float`. Укажи и протестируй выбранное ограничение количества знаков после запятой.

Диалог должен поддерживать такой цикл:

1. Извлечь только данные, которые действительно есть в сообщении пользователя.
2. Если обязательных полей не хватает, сохранить черновик в рамках сессии и спросить только о недостающих данных. Следующий ответ пользователя дополняет тот же черновик.
3. Когда черновик полон, показать все нормализованные поля и предложить явные команды подтверждения и отмены.
4. Сохранить запись только после однозначного подтверждения, например `/save`. `/cancel` удаляет черновик без создания операции.
5. Повторное подтверждение одного черновика не создаёт дубликат. Ошибка или повтор tool-вызова также не должны приводить к двойной записи.
6. Команда просмотра последних записей работает детерминированно и без обращения к LLM. Добавь явную команду исправления ошибки: безопасное удаление по `id` либо создание корректирующей записи. Выбери один простой вариант, опиши его и проверь изоляцию сессий.
7. Обычный вопрос, не содержащий намерения записать операцию, не создаёт черновик и не изменяет базу.

Точные названия дополнительных команд выбери один раз и одинаково используй в CLI, Telegram, help-тексте, тестах и README. Существующие `/start`, `/help`, `/status`, `/reset` и команды памяти не ломай. Явно опиши, влияет ли `/reset` на незавершённый бизнес-черновик; сохранённые операции он удалять не должен.

## Архитектурные требования

- Отдели бизнес-записи от разговорной `MemoryStore`: это разные данные с разным жизненным циклом.
- Общую доменную логику и SQLite-хранилище размести в `shared/`, если их используют несколько интерфейсов. В `08_business_agent/` оставь точку входа, демонстрацию и документацию этапа.
- Используй отдельную SQLite-базу внутри `08_business_agent/data/`; каталог с рабочими данными должен быть исключён из Git. Не смешивай операции с `05_memory/data/memory.sqlite3`.
- SQL использует только параметры, никаких строковых подстановок пользовательских данных. Создание схемы должно быть повторяемым и безопасным при повторном запуске.
- Сессия определяется доверенным приложением: для Telegram — разрешённым user ID, для CLI — явным локальным идентификатором. Модель не может читать или менять чужую сессию.
- Извлечение моделью считай недоверенным предложением. Python повторно проверяет каждое поле до создания черновика и до записи.
- Если добавляешь инструменты, регистрируй их через существующие `ToolDefinition` и `ToolRegistry`. Укажи корректный `Permission`; модель не выдаёт себе разрешение. Не публикуй запись бизнес-данных через MCP в Phase 8.
- Не передавай модели путь к базе, SQL, токены, внутренние исключения и записи других сессий.
- Не добавляй web framework, ORM, Docker, очередь, vector database или новую библиотеку, если задача решается стандартной библиотекой и текущими зависимостями.
- Не меняй модель и настройки рассуждения без доказанной необходимости.
- Сохрани совместимость существующих CLI, Telegram, памяти, инструментов и MCP.

Если для безопасного подтверждения удобнее сделать небольшой специализированный `BusinessAgent` поверх общего runtime, это допустимо. Не прячь запись внутри свободного текстового ответа модели: переходы `draft → confirmed → saved/cancelled` должны быть видны и проверяться кодом.

## Границы Phase 8

В этом этапе реализуй извлечение, уточнение, черновик, подтверждение, сохранение, просмотр последних записей и простой способ исправить ошибочную запись.

Не реализуй:

- сводные показатели, прибыль, группировки и SQL-аналитику;
- отчёты, графики, экспорт и рекомендации;
- автоматические фоновые задачи и уведомления;
- удалённый сервер, многопользовательскую авторизацию и облачное развёртывание;
- банковские интеграции, платежи и любые внешние финансовые действия;
- multi-agent orchestration.

Эти возможности относятся к Phase 9 и более поздним этапам.

## Проверки

Добавь содержательные offline-тесты как минимум для:

- полной операции дохода и расхода;
- каждого отсутствующего обязательного поля и последовательного дополнения черновика;
- нормализации суммы, валюты и относительной даты с фиксированными часами;
- отказа для неверной суммы, даты, валюты, слишком длинных полей и лишних входных полей;
- отсутствия записи до подтверждения;
- `/save`, `/cancel` и повторного `/save` без дубля;
- сохранения после повторного открытия SQLite;
- изоляции двух сессий;
- безопасного параметризованного хранения строк с кавычками и похожим на SQL содержимым;
- просмотра и выбранного способа исправления записей без LLM;
- отсутствия записи из обычного вопроса;
- ошибок SQLite без утечки пути, SQL и сырых исключений пользователю или модели;
- неизменности существующих функций CLI, Telegram, памяти, tools и MCP.

Подмени модель в тестах. Не расходуй OpenAI API, Telegram API и публичную сеть. Не пиши тест, который просто повторяет строки реализации; проверяй наблюдаемое поведение и содержимое временной базы.

После изменений выполни:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
git diff --check
```

Если есть локальная детерминированная демонстрация без API, запусти и её. Не запускай живые внешние запросы без необходимости.
