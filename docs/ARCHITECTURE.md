# Архитектура

## Текущий путь запроса

```text
Telegram → telegram_api → TelegramAdapter ┐
                                          ├→ BusinessAgent ── обычный вопрос → FirstAgent
Терминал → 03_first_agent/main.py ─────────┘       │                         ↓
                                                   │                   OpenAIProvider → модель
                                                   │                         ↓ tool
                                                   │             ToolRouter → MCP / ToolRegistry
                                                   └─ draft/save/list/delete → BusinessStore
```

Общий код находится в `shared/agent_runtime/`; раздел 03 сохраняет совместимые импорты. `BusinessAgent` добавляет сессионный прикладной сценарий поверх неизменённого `FirstAgent`, который по-прежнему управляет общим циклом модели, разрешёнными инструментами и разговорной памятью SQLite. `ToolRegistry` проверяет права и аргументы, `ToolRouter` направляет выбранные READ-вызовы к MCP. Telegram Adapter проверяет числовой user ID и личный чат до любых действий, обрабатывает команды и передаёт обычный текст в `reply()`. Транспорт использует стандартный urllib и long polling. Voice/photo/document пока не реализованы.

Настройки Telegram читаются из окружения с загрузкой только `04_telegram_agent/.env`. События логируются без содержимого запросов и секретов. Один процесс последовательно обрабатывает сообщения; offset хранится в памяти процесса, а последние 10 обменов и факты — в локальной SQLite. Ошибки доставки не повторяют вызов LLM/tools. Инструкция и ограничения: [04 Telegram Agent](../04_telegram_agent/README.md).

## Историческая основа: runtime Phase 3

```text
Пользователь → main.py → FirstAgent → ModelProvider → OpenAI Responses API
                          │                              │
                          └─ CalculatorDispatcher ← вызов функции от модели
                                │
                                └─ CalculatorTool из 01_python_basics
                          результат → модель → окончательный ответ
```

- `main.py` загружает локальный .env, читает ввод и обрабатывает ошибки API.
- `model_provider.py` определяет ModelProvider (небольшой Protocol), ModelReply и адаптер OpenAIProvider. Agent runtime не читает напрямую формат SDK. Адаптер OpenAI включает строгую схему функции и возвращает обычные текстовые ответы или ToolCall.
- `agent.py` последовательно запрашивает модель, передаёт результат инструмента с call_id и заканчивает на текстовом ответе. Максимум три вызова инструмента на пользовательское сообщение. previous_response_id обновляется только после готового ответа.
- `tool_bridge.py` допускает только существующий CalculatorTool и перед выполнением проверяет JSON, имена и размер аргументов. Незнакомые инструменты не исполняются. Это чистый расчёт без побочных действий.
- Предыдущий ответ связывает шаги одного tool loop на стороне [OpenAI Responses API](https://developers.openai.com/api/docs/guides/conversation-state). Между сообщениями текущий агент собирает контекст из локальной SQLite. Протокол вызова функции сверён с [официальным руководством](https://developers.openai.com/api/docs/guides/function-calling) 2026-09-14.

Новый провайдер впоследствии может реализовать `ModelProvider`, возвращая тот же `ModelReply`. Claude и локальные модели пока не подключены. С Phase 5 есть SQLite-память, с Phase 6 — `ToolRegistry`, с Phase 7 — `ToolRouter` и MCP-клиент. Диаграмма выше отражает текущий путь, а здесь сохранён контекст первоначальной реализации.

## Первый пример Python

`01_python_basics/business_operation.py` — отдельная локальная программа без API и записи файлов. Проверка текстовой суммы отделена от вычитания и терминального интерфейса. Для суммы используются Decimal, до 12 цифр целой части и до двух десятичных знаков; неправильный ввод отклоняется без округления. Отрицательная разница допустима. Новых зависимостей нет; переносить код в shared пока не требуется.

## Второй пример Python

`01_python_basics/business_json.py` импортирует проверку и расчёт первого примера. Команда save создаёт JSON с двумя строковыми суммами revenue/expenses, read проверяет файл и заново вычисляет разницу. По умолчанию файл находится в 01_python_basics/data/operation.json; data исключена из Git. Режим создания x предотвращает перезапись. Это одна запись в одном файле без транзакций и конкурентной записи, не общий слой памяти. Код остаётся внутри раздела примеров, поскольку несколько агентов его ещё не используют.

## Третий пример Python

`01_python_basics/calculator_tool.py` содержит CalculatorTool (имя, описание, run) и dataclass ToolResult (ok, value, error). Валидация и вычитание переиспользованы из business_operation.py. Инструмент возвращает данные без ввода/вывода; tool_example.py отвечает за аргументы командной строки и отображение JSON. Это локальная практика классов и модулей, без подключения LLM, registry или permission layer. Перенос в shared потребуется при реальном использовании несколькими агентами.

## Четвёртый пример Python

`01_python_basics/http_example.py` читает HTTP_EXAMPLE_BASE_URL из окружения процесса и получает две учебные задачи GET-запросами. urllib выполняет запросы в рабочих потоках через asyncio.to_thread; gather объединяет результаты. Сетевой таймаут 10 секунд не является строгим общим дедлайном. Ответ ограничен 64 КиБ и проверяется после разбора JSON. Ошибка одного запроса не скрывает второй результат. Новых библиотек и загрузки .env нет. Авторизация, retries и rate limits оставлены для Phase 2. Это пример для доверенной настройки адреса владельцем, а не сетевой инструмент с адресом от LLM.

## Phase 2: API

`02_web_api/api_client.py` — отдельный JSON-клиент с Bearer-заголовком и ограниченными повторами GET. POST не повторяется, так как итог сетевой ошибки может быть неизвестен. Поддержаны Retry-After (секунды/дата), timeout и обработка ошибок без секретов. Перенаправления отключены, HTTP разрешён только на loopback; для внешних адресов нужен HTTPS.

`local_service.py` запускает учебный сервис на 127.0.0.1 и свободном порту. Он хранит задачи в памяти, проверяет токен и входные данные, воспроизводит 429/503/задержку. `demo.py` выполняет реальный POST и проверяет результат через GET, затем показывает обработку ошибок и останавливает сервис. Токен берётся из API_LAB_TOKEN или генерируется в памяти. .env не загружается, зависимостей нет. Это практика HTTP, а не production-сервер или слой бизнес-данных.

## Организация проекта

Разделы `01_...`–`12_...` сохраняем. Общий код переносим в `shared/` при реальном повторном использовании. `tests/` содержит проверки; `docs/` — три основных документа. Старые пустые подразделы docs/architecture, docs/decisions, docs/guides сохранены.

Для нового запуска используем корневое `.venv/`; прежнее `03_first_agent/.venv/` остаётся рабочим локальным вариантом. Оба исключены из Git. Конфигурация чата остаётся в `03_first_agent/.env`; корневой .env.example содержит указатель на настройку чата и безопасный пример HTTP_EXAMPLE_BASE_URL; сам файл не загружается.

## Принятые решения

| Решение | Причина |
|---|---|
| Python 3.11 как базовая версия текущего запуска | Уже установлен и подходит коду; обновление не требуется для Phase 0 |
| Сохраняем OpenAI SDK, python-dotenv и модель прототипа | Нет причины менять подход на этапе подготовки |
| Закрепляем версии трёх прямых зависимостей | OpenAI SDK, python-dotenv и MCP SDK устанавливаются предсказуемо; полное закрепление транзитивных зависимостей пока не вводим |
| unittest из стандартной библиотеки | Проверки без дополнительных зависимостей и расходов на API |
| Три документа вместо шести | Цель хранится в roadmap, решения здесь, история в Git |
| Никаких новых framework, Docker, очередей и vector DB сейчас | Добавляем технологии под конкретный работающий сценарий |

## Направление развития, ещё не реализация

Небольшой контракт модели и адаптер OpenAI уже выделены. Форматы запроса, ответа и вызовов tools принадлежат приложению: будущий адаптер другой модели не должен требовать переписывания бизнес-логики.

CLI и Telegram вызывают общий runtime. Runtime обращается к модели и только к разрешённым инструментам. Валидация и разрешения исполняются кодом до действия. Память уже подключена отдельно; семантический поиск добавим при доказанной необходимости.

Бизнес-данные сохраняются структурированно; деньги рассчитываются через Decimal или целые минимальные денежные единицы и SQL, без арифметики LLM. Позже runtime получает request ID, безопасное логирование, измерение времени и доступную статистику токенов. Multi-agent появляется только при полезном разделении задач.

Перед выбором нового SDK, модели, протокола или инфраструктуры проверяем официальную документацию. Механизм Responses API сверён с официальной документацией 2026-09-14.

## Дополнение Phase 5: локальная память

CLI и Telegram используют `shared/agent_runtime/memory.py`: SQLite хранит последние 10 обменов и явно заданные факты отдельно для каждой сессии. Между вопросами контекст собирается локально, внутри tool loop сохраняется response ID. Команды: `/remember название = значение`, `/memory`, `/forget название`, `/reset`. Данные находятся в `05_memory/data/`, исключены из Git. Полные правила и проверка — в `05_memory/README.md`.

## Phase 6: инструменты и разрешения

Реестр в `shared/agent_runtime/tools.py` объединяет схемы, права и обработчики. `FirstAgent` передаёт доступные схемы `OpenAIProvider` и направляет вызовы модели в `ToolRouter` или напрямую в реестр. Доступны локальные расчёты и преобразования, поиск фактов, запись в подключённую сессию и опциональные публичные GET. `allow_memory_write=False` отключает автоматическую запись; явные команды памяти остаются отдельным путём пользователя. Обработчики сохраняют предметные проверки сумм и источников фактов. Подробности: [06 Tools](../06_tools/README.md).

В `utility_tools.py` добавлены READ-инструменты арифметики, процентов, разницы дат и поиска фактов текущей сессии. Опасные инструменты с requires_confirmation=True и весь класс EXTERNAL заблокированы до реализации подтверждений. Стандартная библиотека Python, новых зависимостей нет.

Следующее расширение: `data_tools.py` содержит конвертацию единиц и статистику; `public_tools.py` — ограниченный PublicClient и четыре справочных API. ApiClient учебного Phase 2 сохранён: его обязательная Bearer-авторизация не подходит публичным сервисам без ключей. PublicClient не предоставляет модели произвольные адреса, отправляет только GET и нормализует ошибки. Все шесть инструментов регистрируются в default_tools, сетевые — только при allow_public_network=True. Схемы и результаты проходят прежний ToolRegistry.

## Phase 7: MCP

`07_mcp/server.py` — локальный stdio-адаптер на официальном MCP Python SDK 2.x. Низкоуровневый сервер публикует `tools/list` из схем `ToolRegistry` и передаёт `tools/call` в тот же реестр. Шесть локальных READ-инструментов доступны по умолчанию; четыре публичных справочных GET требуют флага запуска. MCP-процесс не создаёт MemoryStore и не предоставляет WRITE/EXTERNAL. Результат имеет текстовый JSON и `structuredContent`, исполнение ограничено по частоте и параллелизму. Протокол, установка и подключение описаны в [07 MCP](../07_mcp/README.md).

Для CLI и Telegram `shared/agent_runtime/mcp_client.py` держит один локальный stdio-сеанс в отдельном потоке, потому что текущий `FirstAgent` синхронный. `ToolRouter` заменяет одноимённые локальные схемы и направляет выбранные вызовы через MCP; другие вызовы остаются в `ToolRegistry`. Допуск имён задаётся локальной конфигурацией и ограничен разрешёнными READ-инструментами. Ответы проверяются перед передачей модели. `07_mcp/client.py` — отдельная программа для проверки соединения без модели. `MCP_ALLOW_PUBLIC_NETWORK` управляет сетевыми инструментами CLI и Telegram независимо от `MCP_ENABLED`; Codex запускает сервер по своей отдельной конфигурации.

## Phase 8: бизнес-операции

`shared/agent_runtime/business.py` содержит чистую нормализацию полей, мигрируемый `BusinessStore`, узкий `OpenAIBusinessExtractor` и детерминированный командный `BusinessAgent`. `business_reporting.py` отвечает за периоды, точные отчёты и отдельный строгий read-only extractor вопросов; `business_features.py` — за aliases, бюджеты, шаблоны, CSV и зашифрованные backup; `business_email.py` — за опциональный read-only IMAP и строгую структуру почтового анализа. Результат любого extractor остаётся недоверенным и проверяется Python до чтения с фильтрами или изменения черновика.

`BusinessStore` расширяет существующую схему без потери данных и хранит операции, единственный черновик и audit. `/save` атомарно создаёт операцию либо применяет подготовленное `/edit`; `/delete` ставит `deleted_at`, а `/restore` снимает его. Все пользовательские значения передаются SQL только параметрами. Объект store заранее связан с доверенной сессией (`cli:local` либо `telegram:<allowed user id>`), поэтому методы не принимают чужую session.

Business-команды обрабатываются до общего agent loop. `/draft`, `/save`, `/cancel`, `/list [N]`, `/money` и `/delete ID` не вызывают модель. Старые имена канонизируются через таблицу алиасов. Явное назначение расхода или направление дохода сохраняется в `category`; итоговая команда группирует точные Decimal-суммы по `kind + category + currency`, поэтому валюты не складываются. До AI-вызова локальный маршрутизатор различает очевидный обычный чат, запись операции и read-only вопрос: обычный чат сразу передаётся `FirstAgent`, операция — узкому extractor, вопрос — query extractor. Активный draft всегда имеет приоритет, поэтому краткий ответ дополняет его. `/reset` вызывает прежний сброс диалога и дополнительно удаляет только активный draft. Сохранённые операции и факты остаются. Подробный контракт и запуск: [08 Business Agent](../08_business_agent/README.md).
